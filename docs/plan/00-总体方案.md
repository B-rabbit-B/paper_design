## 1. 选题拆解

论文题目《基于YOLOv8的智能食材识别与膳食分析系统的设计与实现》包含三个必须在系统里落地、在论文里能展开的要素：

| 要素 | 落地要求 | 论文对应章节 |
|---|---|---|
| **YOLOv8 目标检测** | 必须是**自己训练**的权重，而不是直接用官方 COCO 预训练模型；要有数据集构建、训练过程、量化评估（mAP、混淆矩阵、消融实验） | 第 4、6 章，是论文的技术核心与创新点所在 |
| **食材识别** | 识别对象是**生鲜食材**（冰箱/菜篓/案板场景：蔬菜、水果、蛋、肉、水产、豆乳），约 33 类，覆盖国内常见家庭食材 | 第 4 章数据集定义、第 5 章系统实现 |
| **膳食分析** | 识别结果 → 估算份量 → 查营养库 → 热量与三大营养素统计 → 供能比对照《膳食指南》→ 周/月报告 | 第 5 章系统实现、第 6 章系统测试 |

现有项目已经把"食材/食谱数据库 + 营养计算 + 健康画像 + 饮食记录"这一整套膳食分析基础设施做得比较完整（995 种食材、1038 道菜谱、健康目标打分、饮食记录与报告），**唯一明显缺口在识别环节**：现在的 `core/recognizer.py` 只是套了个 ultralytics 的壳子，用的是 COCO 预训练权重，只能识别 7 类里恰好在 COCO 80 类中出现的 5 类（banana/apple/orange/broccoli/carrot），且不返回检测框、不支持自定义类别、不参与份量估算。这意味着：**改造的主战场是"训练一个自己的 YOLOv8 模型 + 把它真正接入系统核心流程"**，而不是重写整个项目。

## 2. 现状分析：直接复用 / 需要改造 / 需要新增

### 2.1 可以直接复用（论文里作为"已有系统基础"简要带过即可，不必重写）

| 模块 | 文件 | 复用点 |
|---|---|---|
| 健康画像 | `core/health_profile.py` | BMI/BMR/理想体重计算，直接用 |
| 健康目标打分权重 | `core/health_goal.py` | 减脂/增肌/控糖/均衡四类目标的打分模型，直接用 |
| 食谱推荐引擎 | `core/recommender.py` | 打分公式（覆盖度+丰富度+利用率+目标匹配+营养适配），直接用 |
| 禁忌过滤 | `core/diet_advisor.py` | 过敏原/慢病过滤逻辑，直接用 |
| 每日规划核心 | `core/daily.py` | TDEE、三餐目标、打卡评分等函数，绝大部分直接用，仅 `parse_manual_items` 需小改 |
| 买菜推荐 | `core/market.py` | 地域时令推荐，与本次改造无关，不动 |
| 数据库连接与既有表 | `database/db.py` | `ingredients`/`recipes`/`users`/`user_profile`/`daily_log` 及其 `ensure_*` 模式，保留并扩展 |
| 食材营养库 | `data/ingredients.json` | 995 条，含热量/蛋白/脂肪/碳水/纤维/GI，是识别结果查营养的基础 |
| 食谱库 | `data/recipes.json` | 1038 道菜，识别到食材后推荐菜谱要用到 |
| 中国食物成分表原始数据 | `data_sources/cfcd/*.json` | 第 6 版，含维生素矿物质字段，是"微量营养素分析"这一新增功能的数据来源 |

### 2.2 需要改造

| 模块 | 现状问题 | 改造方向 | 详见 |
|---|---|---|---|
| `core/recognizer.py` | 只返回名称+置信度，无框坐标；类别硬编码 7 个；COCO 预训练权重；视觉大模型优先、YOLO 是兜底 | 返回完整检测结果（框/类别/置信度/数量）；类别从 `classes.yaml` 读取；自训练权重为主，视觉大模型降级为可选对比/兜底；支持画框可视化 | 03 §B2 |
| `core/nutrition.py` | `calc_total` 固定按 100g 计算，无法区分每种食材的实际份量 | 支持每项独立克数，接入"数量 × 默认单重"的份量估计 | 03 §B3 |
| `app.py` 的 `/recognize` | 先调大模型、失败才用 YOLO；无 API key 时体验受限 | 反转优先级：YOLO 为主路径；新增 JSON API 供前端异步调用 | 03 §B6 |
| `app.py` 的 `/daily` | 拍照记录完全依赖视觉大模型估热量 | 备菜照片先走 YOLO 识别+份量估算，无法识别（如已烹饪成品菜）时才回退大模型 | 03 §B6 |
| `config.py` | `YOLO_MODEL` 是相对路径（依赖启动目录）；`CLASS_TO_INGREDIENT` 硬编码 7 类 | 改绝对路径；类别映射迁移到 `training/classes.yaml` 单一真源 | 03 §B8 |
| `templates/index.html`、`daily.html` | 识别结果只是文字回填，无可视化、无克数编辑 | 增加检测框图展示、可编辑克数表、供能比展示 | 03 §B7 |

### 2.3 需要新增

| 新增内容 | 目的 | 详见 |
|---|---|---|
| `training/` 训练工程（数据集处理、训练、评估、导出脚本） | 支撑"自己训练模型"这一论文核心，产出实验数据和图表 | 01、02 |
| `models/` 权重与模型卡目录 | 存放自训练权重，供系统运行时加载 | 02、03 |
| `core/food_classes.py` + `training/classes.yaml` | 类别定义的唯一真源，训练与运行时共用，避免类别映射两处维护 | 01 §6、03 §B1 |
| `core/analysis.py` | 三大营养素供能比、周/月报告聚合、微量营养素对照，是"膳食分析"新增的分析深度 | 03 §B4 |
| `database` 新增两张表：`recognition_log`、`meal_item` | 记录每次识别结果和每餐食材明细，是识别数据能沉淀进膳食分析的关键（现有 `daily_log` 只存每日一行汇总） | 03 §B5 |
| `/report` 页面 + ECharts | 周报/月报可视化，答辩演示效果 | 03 §B6、B7 |
| `data/micronutrients.json` + 抽取脚本 | 从 `data_sources/cfcd` 中提取钙铁锌维C等微量营养素，支撑营养分析深度 | 03 §B4 |

## 3. 目标系统架构

```
┌─────────────────────────── 表示层 ───────────────────────────┐
│  Jinja2 服务端渲染页面（沿用现有 10 个页面 + 新增 report.html） │
│  ECharts（本地 vendor，答辩离线可用）                          │
└───────────────────────────┬───────────────────────────────────┘
                             │ HTTP（Flask 路由）
┌───────────────────────────▼───────────────────────────────────┐
│                        应用层 app.py                            │
│  /recognize  /api/recognize  /recommend  /daily  /api/meal_item │
│  /report  /api/model_info  /profile  /market  /week  /chat 等   │
└───────┬──────────────┬──────────────┬──────────────┬───────────┘
        │              │              │              │
┌───────▼──────┐ ┌─────▼──────┐ ┌─────▼──────┐ ┌─────▼──────────┐
│ recognizer.py │ │nutrition.py│ │ analysis.py │ │ recommender.py  │
│ (YOLOv8 主路径│ │(份量估算+  │ │(供能比/周月 │ │ diet_advisor.py │
│  +可选大模型) │ │ 营养查询)  │ │ 报/微量营养)│ │ daily.py 等     │
└───────┬──────┘ └─────┬──────┘ └─────┬──────┘ └─────┬──────────┘
        │              │              │              │
┌───────▼──────────────▼──────────────▼──────────────▼───────────┐
│                          数据层                                  │
│  SQLite（ingredients/recipes/users/daily_log/                   │
│          recognition_log/meal_item 新表）                        │
│  JSON（ingredients.json / recipes.json / micronutrients.json）  │
│  models/best.pt（自训练权重）· training/classes.yaml（类别真源）│
└────────────────────────────────────────────────────────────────┘
                             │（可选旁路，无 key 时完全不影响主流程）
                    ┌────────▼────────┐
                    │  DeepSeek 大模型  │
                    │ （对话/文案/兜底）│
                    └──────────────────┘
```

**核心设计原则**：YOLOv8 自训练模型是识别环节的主路径且系统在无 API key 时完整可用；DeepSeek 降级为可选增强（点评文案、体检单解析、YOLO 未命中时的兜底）。这样论文的技术贡献清晰地落在"自训练检测模型 + 其驱动的膳食分析"上，而不会被质疑"其实是大模型在做识别"。

## 4. 技术路线

| 层面 | 选型 | 说明 |
|---|---|---|
| 检测模型 | Ultralytics YOLOv8（`ultralytics` 包，2026-09 核实最新 `8.4.161`） | 包内同时支持 YOLOv3/v5/v8/11/26，YOLOv8 未被移除，`YOLO("yolov8n.pt")` 训练/推理照常可用；可选做 YOLOv8 vs YOLO11 的对比实验（同一套代码，见 02 §6 E3） |
| 训练框架 | PyTorch（训练机走 CUDA，见 02） | 本地 RTX 4060（8GB）训练 |
| 部署推理 | PyTorch CPU（当前开发机）+ 可选 ONNX Runtime | 开发机无独立 GPU，需要保证 CPU 推理速度可接受（见 02 目标指标） |
| 开源协议 | YOLOv8 为 AGPL-3.0 | 对本科毕设无影响：非商业用途、代码随论文公开即满足 AGPL 的开源要求；仅当做成闭源商用产品时才需购买 Ultralytics 企业授权。论文"技术选型"或"开源协议"小节写一句说明即可 |
| Web 框架 | Flask 3 + 原生 SQL（sqlite3）+ Jinja2 | 保持不变，不引入 ORM 或前端框架，改造成本最低 |
| 图表 | ECharts（本地 vendor 文件） | 现有项目无任何图表库，周报/月报可视化新增 |
