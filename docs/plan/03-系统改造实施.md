### B3. `core/nutrition.py`（改造 `calc_total`，新增两个方法）

```python
@staticmethod
def calc_total(items, grams=100.0):
    """grams 支持三种形式：float（所有食材统一按此克数，兼容旧调用）｜ dict{食材名: 克数}｜
    忽略 grams 参数，优先使用每个 item 自带的 "grams" 字段（新识别流程走这条路径）。"""

@staticmethod
def scale(nutrient_dict, grams) -> dict:
    """单个食材按实际克数换算：{calories, protein, fat, carb, fiber}（原表按 100g 存储，乘以 grams/100）。"""

def items_with_grams(self, det_items, grams_override=None) -> tuple[list, list]:
    """det_items: recognizer.detect()["items"]；grams_override: {食材名: 用户修改后的克数}（页面表单提交）。
    返回 (matched, missing)：matched 每项含 name/count/grams/confidence/cls/unit 及营养值，
    missing 是在 ingredients.json 中查不到的食材名列表。"""
```

**份量估计策略**（写入论文"份量估计方法"小节，明确其为半自动方案而非精确称重）：`grams = count × default_weight_g`（`unit=piece` 的可计数食材，如鸡蛋、苹果）或直接取 `default_weight_g`（`unit=bulk` 的整份食材，如西兰花、生姜、肉类）。默认值来自 `classes.yaml`，用户可在识别结果页面手动修改克数，营养计算实时按修改后的值重新计算。不做基于检测框面积或深度学习的重量估计，避免超出本科毕设合理工作量，同时把"用户修正"作为准确性的最后一道保障。

```sql
CREATE TABLE IF NOT EXISTS recognition_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
```

## D. 风险与对策

| 风险 | 对策 |
|---|---|
| 类别数据量不均衡（蛋/肉/水产类图片远少于果蔬类） | `summary.json` 量化后对稀少类做过采样（`prepare_dataset.py --oversample cls:2`）；Open Images 定向补图；自采集时优先拍这些稀缺类；论文中报告各类别 AP 而不是只报整体 mAP |
| 公开数据集（单品白底图/国外自然场景）与国内冰箱/菜篓场景存在域偏移 | E4 实验量化差距大小；自采数据一半用于微调（E5）；训练时开启 `hsv`/`scale`/`mosaic` 等增强模拟不同光照和遮挡；部署阈值按 E7 在自采冰箱测试集上确定 |
| 开发机无独立 GPU，CPU 推理可能偏慢 | 上传图片长边限制 1280；部署优先用 yolov8n（体积小）；可选切换到 ONNX（E6 已验证性能差异）；应用启动时预热一次推理（用空白图跑一次 `detect`）；保留现有的接口限流机制 |
| 训练时的英文类名映射不到 `ingredients.json` 现有食材名 | `food_classes.validate()` 在应用启动和数据准备时都会检查并警告；`ingredient` 字段允许填现有别名而不强制改 `ingredients.json` 主名；缺失时优先在 JSON 里补别名而不是改代码逻辑 |
| Windows 上 ultralytics/torch/torchvision 版本不兼容 | 训练机先按官方 CUDA 索引装匹配驱动版本的 torch+torchvision，再装 `ultralytics>=8.3`；开发机保持现有 CPU 版 torch 不动，只补装 ultralytics 相关依赖；训练脚本严格遵守 `if __name__ == "__main__":` 入口守卫 |
| ultralytics 运行时的联网行为（检查更新、下载字体等）在答辩现场断网时报错 | 画框标签用自实现的 PIL 绘制而非依赖联网下载字体的 `result.plot()`；训练/推理前执行 `yolo settings sync=False`；模型权重通过本地文件加载，不依赖运行时联网下载 |
| Flask 开发服务器多线程下并发调用 YOLO 推理可能崩溃 | `IngredientRecognizer` 内部用 `threading.Lock` 包裹 `predict` 调用；答辩演示建议单人操作，避免并发请求 |
| 份量估计（数量×默认单重）的准确性被答辩老师质疑 | 论文中明确说明这是"半自动份量估计"方案：系统给出参考值，用户可在页面手动修正，并非声称达到精确称重级别的准确度；可选做一次简单的用户修正前后误差对比作为讨论素材 |
| 已烹饪的成品菜（如 `/daily` 的餐食照片）YOLO 训练集是生鲜食材，识别不出 | `/daily` 页面文案明确定位为"备菜照片"场景；只有在 YOLO 检测为 0 框时才可选调用视觉大模型兜底；同时保留手动填写"食材 300g"的路径，保证无 API key 时依然可用 |
| Service Worker 缓存旧版 CSS/JS，改动后浏览器显示旧样式 | `static/sw.js` 的 `CACHE_NAME` 常量每次有静态资源改动时递增版本号；答辩前提醒浏览器强制刷新一次 |
| `static/uploads` 目录随使用不断增长占用磁盘 | 上传时统一限制长边 1280 并转 JPEG 压缩（单张约 200KB 量级）；README 中说明可手动清理；不做自动定时清理（避免超出需求的投机功能） |
| 训练数据集或大体积权重文件被误提交进 git 仓库 | `.gitignore` 已包含 `*.pt/*.onnx/*.pth`，并补充 `training/datasets/`、`training/runs/`、`static/uploads/`；提交前用 `git status` 检查确认无大文件被跟踪 |
