## 1. 使用规则

### 1.1 门禁：严格串行

```
阶段0 ──验收──▶ 阶段1 ──验收──▶ 阶段2 ──验收──▶ 阶段3 ──验收──▶ 阶段4 ──验收──▶ 阶段5 ──验收──▶ 完成
环境与骨架      数据集构建      训练与评估      识别接入        膳食分析        实验与文档
```

- 阶段 N 的验收清单**全部勾选**、验收记录**填写完整**、**独立审查通过**（§1.5），并且分支已合并回 master（§1.3）之后，才能开始阶段 N+1。
- 清单里没有"可选"项。某一项确实不适用时，在验收记录的备注里写明原因，并得到导师或自己书面确认后，再标成 `[x]`，不能直接跳过。
- 不允许"先把下一阶段做着，回头再补验收"。

### 1.2 证据要求

- 每个清单项都有编号，比如 **0.3**。勾选之前，把证据存进 `docs/acceptance/stage-N/`，文件名以编号开头。例如 `0.3-yolo-names.txt`、`3.4-识别结果截图.png`。
- 命令类证据用 `Tee-Object` 同时显示并保存输出（PowerShell）：

```powershell
python -c "from ultralytics import YOLO; print(YOLO('models/yolov8n.pt').names[46])" | Tee-Object docs/acceptance/stage-0/0.3-yolo-names.txt
```

- 页面类证据保存截图。证据文件随阶段验收一起提交，这些材料可以直接用作论文"系统测试"章节的附图。

### 1.3 分支与合并

每个阶段都在自己的分支上完成，master 只接收已通过独立审查的阶段合并，**不直接在 master 上提交**。master 上唯一的非合并提交是基线提交，即导入原项目代码与规划文档的那一次。

| 阶段 | 分支名 |
|---|---|
| 0 | `stage-0-env` |
| 1 | `stage-1-dataset` |
| 2 | `stage-2-train` |
| 3 | `stage-3-recognize` |
| 4 | `stage-4-analysis` |
| 5 | `stage-5-experiments` |

一个阶段的完整流程如下：

1. **开分支**：确认上一阶段的标签已存在，然后从 master 切出本阶段分支。

```powershell
git checkout master
git checkout -b stage-N-xxx
```

2. **做任务、留证据**：阶段内的所有提交都放在这个分支上。每提交一次之前都执行 `git status`，确认没有 `.pt`、`.onnx` 或数据集图片被加入。
3. **自查**：勾选本文档中该阶段的清单项，填写"验收记录"表，结论栏先写"待审查"，然后提交。
4. **独立审查**：按 §1.5 请审查代理审查。审查报告写入 `docs/acceptance/stage-N/supervisor-report.md`。
5. **审查不通过**：留在本分支上修复，然后重新审查。新报告追加 `-r2`、`-r3` 等后缀，旧报告保留，不要删除或改写。
6. **审查通过**：把验收记录的结论栏改为"通过"，在备注中写上审查报告的文件名并提交。然后合并回 master，在合并提交上打标签：

```powershell
git checkout master
git merge --no-ff stage-N-xxx -m "合并阶段 N：<阶段名>"
git tag stage-N-pass
```

合并时使用 `--no-ff`，这样 master 的历史中每个阶段都保留一次独立的合并提交，可以直接看出每个阶段改了哪些内容。

### 1.4 回溯重验规则

后续阶段如果改动了前面阶段的产出物，必须按下表重跑受影响的清单项。回溯修改在当前阶段的分支上完成，重跑的清单项一并纳入当前阶段的独立审查范围。审查通过、合并回 master 后，在同一个合并提交上再补打一个标签，例如 `stage-2-pass-r2`。

| 改动内容 | 需要重跑的清单 |
|---|---|
| `training/classes.yaml`（增删类、改类名、改 id 顺序） | 从阶段 1 开始的全部阶段（数据集要重建，模型要重训） |
| `training/classes.yaml` 中只改 `zh`、`default_weight_g` 这类不影响训练的字段 | 0.6、3.4、3.5 |
| 替换 `models/best.pt`（比如换成阶段 5 的微调模型） | 2.9 到 2.13、阶段 3 全部、阶段 5 中受影响的实验 |
| `database/db.py` 的表结构 | 阶段 4 全部 |
| `data/ingredients.json` | 0.5、0.6，以及用到具体营养数值的 3.5、4.4、4.5 |

### 1.5 独立审查

阶段是否通过，不由执行工作的 Claude 会话自己判断，而由一个**独立的 Claude 审查代理**来判断。它的定义在 `.claude/agents/stage-supervisor.md`。

- **怎么调用**：在 Claude Code 中说"请用 stage-supervisor 审查阶段 N，分支 stage-N-xxx"。如果当前会话看不到这个代理，可以新开一个会话提出同样的要求，或者把该文件的内容作为指令交给一个通用子代理。
- **审查代理要做的事**：
  - 自己重新执行每一个能在本机执行的验收命令，把结果与预期和证据文件逐一对比。已经勾选的项也要复核。
  - 本机执行不了的项，比如训练机上的检查，改为核对证据文件的内容。
  - 审阅本分支相对 master 的全部改动，检查有没有越界修改、明显缺陷，有没有权重、数据集或密钥被提交。
  - 把报告写入 `docs/acceptance/stage-N/`。
- **审查代理不做的事**：不修改代码和文档，不提交、不合并、不打标签。审查报告写好后，执行者也不得修改报告内容。
- **结论规则**：只要有一项"不通过"，或者有"无法验证"且没有可接受的理由，整体结论就是"不通过"。
- **中期审查**：阶段中途需要等待外部条件时（比如阶段 0 要等训练机），可以先对已完成的项做一次中期审查，报告写入 `supervisor-report-interim.md`。中期审查不能代替最终审查。

## 3. 阶段 0：环境与骨架

### 进入条件

- 已读完 00–03 四份规划文档。
- `E:\paperdesign` 已从原项目复制完成，git 仓库已初始化（已完成）。
- 训练机（RTX 4060）能正常开机并联网。

### 任务

1. **开发机**：
   - 在项目根目录建 venv。
   - 先按 CPU 索引装 torch 和 torchvision，再执行 `pip install -r requirements.txt`，安装顺序见 03 §B9。
   - 把 `requirements.txt` 按 03 §B9 补上 `pyyaml`。
2. **COCO 兜底权重**：把 `scripts/download_model.py` 的输出路径改成 `models/yolov8n.pt`，然后运行一次。
3. **类别定义**：
   - 按 01 §1 的 33 类表格和 01 §6 的字段格式，编写 `training/classes.yaml`。
   - 按 03 §B1 实现 `core/food_classes.py`。
4. **营养库别名**：
   - 在 `data/ingredients.json` 中，给"鸡"的 `aliases` 加上 `"鸡肉"`，给"草鱼"的 `aliases` 加上 `"鱼"`。已核实这两个条目当前的 `aliases` 都为空。
   - 修改后执行 `python database/init_db.py` 重新灌库。**这一步不能省**：系统通过 `database/db.py` 的 `load_ingredients(conn)` 读取 SQLite 表，不直接读 JSON。该脚本只重建食材表和菜谱表，不影响用户数据。
5. **训练机**：按 02 §1 搭好 CUDA 版 PyTorch 和 ultralytics 环境。
6. **两台机器**都执行 `yolo settings sync=False`。训练机上的自检脚本会自动完成这一步。
7. **提交与交付代码**：在 `stage-0-env` 分支上提交，然后把同一份代码交给训练机。
   - **推荐方式：git bundle。** 在开发机上执行 `git bundle create paperdesign.bundle --all`，把生成的文件拷到训练机，再执行 `git clone paperdesign.bundle paperdesign`。克隆出来的仓库默认就在 `stage-0-env` 分支上，工作区按训练机自己的 git 设置检出，不会出现换行符导致的误报。
   - bundle 里不包含权重文件。可以单独把开发机上的 `models/yolov8n.pt` 拷到训练机的同一路径下，也可以在训练机上运行 `python scripts/download_model.py` 下载。
   - **备选方式：直接拷贝整个仓库文件夹**，不带 `.venv`。这种方式的问题是：如果训练机的 `git config core.autocrlf` 与开发机不同，git 会把大量文件误报为"已修改"，导致 0.13 失败。开发机上这个值是 `true`。
8. **训练机自检脚本**：编写 `training/check_env.py`，它一次完成训练机上的全部检查，并写出证据文件。
