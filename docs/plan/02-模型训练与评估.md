# 02 模型训练与评估

> 训练机：用户本地 RTX 4060（8GB 显存）。当前开发机（Intel UHD 730 核显，`torch 2.14.0+cpu`）不具备训练能力，仅用于开发与 CPU 推理部署，本文档的训练命令均在 4060 机器上执行，训练产出的权重再拷贝回开发机 `models/` 目录。

## 1. 训练机环境搭建（RTX 4060）

```bash
# 1. 建虚拟环境
python -m venv .venv
.venv\Scripts\activate          # Windows

# 2. 安装匹配显卡驱动的 CUDA 版 PyTorch
# 先查驱动支持的 CUDA 版本：nvidia-smi 右上角 "CUDA Version"
# 以 CUDA 12.1 为例（RTX 4060 常见驱动可支持到 12.x）：
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121

# 3. 验证 CUDA 可用
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
# 期望输出包含 True 和 "NVIDIA GeForce RTX 4060"

# 4. 安装 ultralytics（会带上其余依赖，但不会覆盖已装好的 CUDA 版 torch）
pip install "ultralytics>=8.3"

# 5. 关闭 ultralytics 的联网行为（检查更新、遥测），避免训练环境不稳定网络时报错/卡顿
yolo settings sync=False
```

**Windows 注意事项**：
- 训练脚本入口必须有 `if __name__ == "__main__":` 守卫（ultralytics 内部用多进程 DataLoader，Windows 下缺少这个守卫会报错或死循环）。
- `workers` 参数不要设太高，4060 机器 CPU 核心数有限时设 `workers=4` 或更低，避免数据加载成为瓶颈或内存溢出。
- 首次运行 `YOLO("yolov8n.pt")` 会自动联网下载官方预训练权重（约 6MB），确保训练机能联网这一次，或提前从 ModelScope 镜像（https://modelscope.cn/models/AI-ModelScope/YOLOv8 ）下载好放到项目目录。

## 2. 显存与训练耗时预估（8GB 显存）

| 模型 | 建议 batch（imgsz 640） | 显存占用（AMP 默认开） | 约 1.5 万图训练 120 epoch 预估耗时 |
|---|---|---|---|
| yolov8n | 32 | 约 4–5GB | 约 4–6 小时 |
| yolov8s | 16 | 约 5–6GB | 约 8–10 小时 |
| yolov8m | 8（或降 imgsz 到 512） | 约 6–7GB | 约 15–20 小时，建议夜间跑或分两晚 |

显存不足时（`CUDA out of memory`）优先降 `batch`，其次降 `imgsz`；`ultralytics` 训练默认开启 AMP 混合精度，一般不需要手动开关。`patience=20`（20 轮无提升自动早停）可以有效避免 yolov8m 跑满全部 epoch 浪费时间。

## 3. `train.py` 训练脚本设计

**核心命令**：

```bash
python training/train.py --model yolov8n.pt --data training/data.yaml \
    --epochs 120 --imgsz 640 --batch 32 --name v8n_full

python training/train.py --model yolov8s.pt --data training/data.yaml \
    --epochs 120 --imgsz 640 --batch 16 --name v8s_full

python training/train.py --model yolov8n.pt --data training/data.yaml \
    --epochs 120 --imgsz 640 --batch 32 --no-aug --name v8n_noaug     # 消融对照

python training/train.py --model yolo11n.pt --data training/data.yaml \
    --epochs 120 --imgsz 640 --batch 32 --name v11n_full              # 架构对比

python training/train.py --model models/best.pt --data training/data_ft.yaml \
    --epochs 40 --imgsz 640 --lr0 0.002 --name v8n_ft                 # 自采数据微调
```

**内部封装的 `model.train()` 关键参数**：

```python
model.train(
    data=data_yaml, epochs=epochs, imgsz=imgsz, batch=batch,
    patience=20, optimizer="auto", lr0=0.01, cos_lr=True,
    close_mosaic=10, mosaic=1.0, mixup=0.1,
    hsv_h=0.015, hsv_s=0.7, hsv_v=0.4, fliplr=0.5,
    degrees=0, scale=0.5, translate=0.1,
    workers=4, device=0, project="training/runs", name=name,
    exist_ok=True, seed=0, deterministic=True, pretrained=True,
)
```

`--no-aug` 时把 `mosaic=mixup=hsv_h=hsv_s=hsv_v=fliplr=scale=translate=0`，`--no-mosaic` 时只把 `mosaic=mixup=0`，两者与全部增强的 `v8n_full` 一起构成数据增强消融实验（E2）的三组对照。断点续训加 `resume=True`（ultralytics 会自动定位 `runs/<name>/weights/last.pt`）。`--install` 参数训练完成后自动把 `runs/<name>/weights/best.pt` 复制到 `models/best.pt`。

## 4. `evaluate.py` 评估脚本设计

```bash
# 在公开数据集测试集上评估
python training/evaluate.py --weights models/best.pt --data training/data.yaml --split test --name v8n_test

# 在自采冰箱测试集上评估（域偏移实验）
python training/evaluate.py --weights models/best.pt --data training/data_fridge.yaml --split val --name v8n_fridge

# CPU 推理速度测试（部署机场景）
python training/evaluate.py --weights models/best.pt --speed --device cpu --n 50 --imgsz 640

# 置信度阈值扫描（决定部署时 config.YOLO_CONF 取值）
# 用自采集的 eval 半集，这样即使部署的是微调模型也不会数据泄漏
python training/evaluate.py --weights models/best.pt --sweep-conf 0.25 0.35 0.5 --data training/data_fridge_eval.yaml

# 更新模型卡（供系统 /api/model_info 展示）
python training/evaluate.py --weights models/best.pt --update-card
```

内部调用 `model.val(data, split, imgsz=640, batch=16, conf=0.001, iou=0.6, plots=True, device, workers=0)`，从返回对象取 `box.map50`（mAP50）、`box.map`（mAP50-95）、`box.mp`（精确率）、`box.mr`（召回率）、`box.ap50`（各类 AP50）、`confusion_matrix.matrix`（混淆矩阵）。ultralytics 会自动在 `runs/val/` 下产出 `confusion_matrix.png`、`PR_curve.png`、`F1_curve.png`，脚本把这些图复制到 `training/reports/<name>/` 并额外写出：
- `metrics.json`：整体指标汇总
- `per_class.csv`：每类 AP，列含中文名（从 `classes.yaml` 取）

`--speed` 模式：先用 5 张图预热模型，再对 N 张图逐张推理，统计 `result.speed`（预处理/推理/后处理三段耗时）的均值与中位数，换算 FPS，并打印 `torch.get_num_threads()`（CPU 场景下线程数会显著影响速度，论文报告时需注明测试环境的 CPU 型号和线程数）。

`--update-card` 输出 `models/model_card.json`：

```json
{
  "version": "v8n_full-20261201",
  "arch": "yolov8n",
  "weights": "models/best.pt",
  "classes": 33,
  "imgsz": 640,
  "map50": 0.742,
  "map50_95": 0.518,
  "precision": 0.79,
  "recall": 0.71,
  "cpu_ms_mean": 187.3,
  "fridge_map50": 0.63,
  "trained_at": "2026-12-01",
  "epochs": 120,
  "dataset_summary": {"train_images": 14200, "classes": 33}
}
```

此文件被 `core/recognizer.py` 的 `model_info()` 读取，供 `/api/model_info` 路由和答辩演示直接展示"当前模型 / mAP / 类别数 / 平均推理耗时"。

## 5. `export.py` 导出脚本设计

```bash
python training/export.py --weights models/best.pt --imgsz 640 --opset 12 --simplify --bench --n 50
```

调用 `YOLO(weights).export(format="onnx", imgsz=640, opset=12, simplify=True, dynamic=False)` 产出 `models/best.onnx`。`--bench` 模式对同一批测试图分别用 `.pt`（PyTorch CPU）和 `.onnx`（ONNX Runtime CPU）推理，输出 `training/reports/export_bench.csv`，记录：格式、文件大小（MB）、平均推理耗时（ms）、FPS、与 `.pt` 结果的类别计数一致率（判断 ONNX 转换是否掉精度）。这组对比数据支撑论文"模型部署优化"小节，也决定 `config.YOLO_MODEL` 最终用 `.pt` 还是 `.onnx` 部署。

## 6. 论文第 6 章实验矩阵

| 编号 | 实验内容 | 变量 | 固定条件 | 输出指标 |
|---|---|---|---|---|
| E1 | 模型规模对比 | yolov8n / yolov8s / yolov8m | 同数据、120 epoch、imgsz 640 | mAP50、mAP50-95、参数量、GFLOPs、CPU 推理耗时 |
| E2 | 数据增强消融 | 全部增强 / 关闭 mosaic+mixup / 全部关闭 | yolov8n，其余同 E1 | mAP50-95、训练收敛曲线（`results.png`） |
| E3 | 检测架构对比 | YOLOv8n vs YOLO11n（同一 ultralytics 包） | 同数据、同训练参数 | mAP、CPU 推理耗时 —— 作为"技术选型合理性"的补充论证 |
| E4 | 域偏移评估 | 公开数据集测试集 vs 自采冰箱测试集 | 均用 `best.pt` | mAP 下降幅度、各类 AP 对比表 |
| E5 | 微调增益 | 用 50% 自采数据微调 40 epoch，在另外 50% 自采数据上评估，对比微调前后 | | mAP 提升幅度 |
| E6 | 部署格式对比 | `.pt` vs `.onnx`（均在 CPU 上） | | 推理耗时、FPS、文件体积、结果一致率 |
| E7 | 置信度阈值选择 | conf ∈ {0.25, 0.35, 0.5} | 在自采冰箱测试集上 | Precision/Recall/F1 曲线 → 确定部署时的 `config.YOLO_CONF` |
| E8 | 系统级端到端测试 | `/api/recognize` 从上传到返回结果的总耗时；`recognition_log` 表的统计数据 | 真实使用场景 | 端到端响应时间、平均检测框数 |

## 7. 目标指标（用于判断"训练是否达标可以进入下一阶段"）

- 公开数据集测试集：`mAP50 ≥ 0.70`（yolov8n 基线）
- 自采冰箱测试集（经过微调后）：`mAP50 ≥ 0.60`
- CPU 单张图推理耗时：`≤ 300ms`（640 分辨率，用于判断部署到开发机是否流畅）

若首轮训练达不到这些指标，优先排查：类别数据量是否够（参考 01 §7 每类至少 200 框的验收标准）、标注质量（随机抽查）、是否存在类别定义模糊导致互相混淆（如 `cabbage` 和 `lettuce` 视觉相似）。必要时合并易混淆类别或减少总类别数，而不要盲目加大训练轮数。

## 8. 权重与产出物交接（4060 训练机 → 开发机）

训练机只需要把以下文件拷贝回开发机（通过 U 盘、局域网共享或云盘均可）：

```
training/runs/<name>/weights/best.pt   →  开发机 models/best.pt
training/runs/<name>/results.csv        →  开发机 training/reports/<name>/
training/runs/<name>/results.png        →  开发机 training/reports/<name>/
training/runs/<name>/confusion_matrix.png → 开发机 training/reports/<name>/
training/runs/<name>/args.yaml          →  开发机 training/reports/<name>/
```

`training/datasets/`（原始图片和标注）和 `training/runs/`（完整训练日志，含大量中间权重）体积很大，**不需要**、也不应该拷回开发机或提交进 git 仓库（已在 `.gitignore` 中排除）；只有 `training/reports/` 下整理出的图表和指标文件需要入库，作为论文素材和答辩证据。
